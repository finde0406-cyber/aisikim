# AI시킴 스타터팩 대표 5개 프리미엄 초안 v2

## 1. 문서 목적
이 문서는 스타터팩 우선 제작 15개 중 가장 중요한 대표 5개를 `실제 판매 기준`에 맞춰 한 단계 더 고도화한 프리미엄 초안입니다.  
이 문서의 목적은 유료 상품이 단순한 문장 모음이 아니라, 사용자가 결과물을 더 잘 완성하도록 돕는 `실행형 세트`처럼 느껴지게 만드는 것입니다.

## 2. 이 문서의 사용 방식
- 지금 당장 가장 급한 작업과 가까운 항목 1개를 고릅니다.
- `바로 복사할 본문`을 먼저 사용합니다.
- 첫 결과가 약하면 `후속 질문`으로 구체화합니다.
- 방향은 맞지만 부족하면 `수정 요청`을 사용합니다.
- 마지막에는 `검수 요청`으로 완성도를 끌어올립니다.

## 1. 블로그 글의 첫 구조를 잡고 싶을 때

### 한 줄 설명
글 주제는 정했지만 제목, 소제목, 흐름이 막막할 때 가장 먼저 꺼내 쓰는 초안 생성형 작업지시서입니다.

### 이런 상황에서 특히 잘 맞습니다
- 블로그를 자주 쓰지 않는 사람
- AI가 너무 뻔한 블로그 구조만 줄 때
- 초안을 빨리 만든 뒤 직접 다듬고 싶은 사람

### 이 작업지시서로 기대할 수 있는 결과
- 제목 후보 5개
- 가장 적합한 제목 1개와 이유
- 소제목 구조
- 도입부 초안
- 본문 핵심 흐름
- 마무리 방향

### 언제 쓰는지
- 블로그 글의 첫 질문 단계
- 주제는 정했는데 구조가 안 잡히는 시점

### 바로 복사할 본문
```text
지금 저는 [주제]에 대한 블로그 글을 작성하려고 합니다.
이번 글의 목적은 [정보 제공 / 제품 소개 / 경험 공유 / 문제 해결]입니다.
이 글을 읽을 대상은 [대상 독자]이며, 이 독자는 [현재 수준 / 관심사 / 자주 겪는 문제]를 가지고 있습니다.

이 글을 읽은 뒤 독자가 얻어가야 하는 핵심은 [한 줄 핵심 메시지]입니다.

먼저 이 글에서 반드시 다뤄야 할 핵심 포인트가 무엇인지 짚어주세요.
그 다음 아래 순서로 결과를 작성해 주세요.

1. 제목 후보 5개
2. 그중 가장 적합한 제목 1개와 선택 이유
3. 소제목 구조
4. 도입부 초안
5. 각 소제목별 핵심 문장
6. 마무리 문장

답변은 너무 추상적이지 않게, 실제 블로그 초안으로 바로 옮겨 쓸 수 있을 정도로 구체적으로 작성해 주세요.
읽는 사람이 중간에 이탈하지 않도록 흐름이 자연스럽게 이어지게 해주세요.
가능하면 흔한 표현보다는 실제 상황과 연결되는 문장으로 써주세요.
```

### 바꿔야 할 부분
- `[주제]`: 예) AI로 블로그 글쓰기, 직장인 아침 루틴
- `[정보 제공 / 제품 소개 / 경험 공유 / 문제 해결]`: 글 목적
- `[대상 독자]`: 예) AI 초보자, 직장인, 1인 사업자
- `[현재 수준 / 관심사 / 자주 겪는 문제]`: 독자 설명
- `[한 줄 핵심 메시지]`: 독자가 얻어가야 할 핵심

### 후속 질문
- 위 구조를 유지한 채 도입부만 더 강하게 다시 써줘.
- 소제목은 유지하고, 각 소제목 아래에 들어갈 실제 사례를 더 추가해줘.

### 수정 요청
- 너무 흔한 블로그 표현은 줄이고 실제 경험이 느껴지는 표현으로 바꿔줘.
- 모바일에서 읽기 쉽게 문단 길이를 더 짧게 나눠줘.

### 검수 요청
- 이 글 구조에서 빠진 핵심 요소가 있는지 점검해줘.
- 대상 독자가 읽었을 때 공감이 약할 부분이 있다면 짚어줘.

### 자주 하는 실수
- 주제만 넣고 독자 설명을 비워둔다
- 목적 없이 “그냥 글 써줘” 식으로 요청한다
- 첫 결과만 보고 끝낸다

### 이 순서에서 쓰면 좋습니다
1. 이 작업지시서로 초안을 만든다
2. 제목 후보 확장형 또는 독자 맞춤 수정형으로 이어간다
3. 마지막에 검수형 작업지시서로 마무리한다

### 사용 팁
블로그는 초안보다 `후속 질문`에서 품질 차이가 크게 납니다.  
제목, 도입부, 마무리를 한 번씩 따로 더 요청하면 무료 결과와 확실히 다른 퀄리티를 만들 수 있습니다.

## 2. 업무 보고서의 기본 구조를 잡고 싶을 때

### 한 줄 설명
상사나 팀이 바로 이해할 수 있는 보고서 구조를 빠르게 잡아주는 실무 초안 생성형 작업지시서입니다.

### 이런 상황에서 특히 잘 맞습니다
- 내용을 알고는 있지만 문서 구조가 안 잡힐 때
- 보고서를 짧은 시간 안에 초안 수준으로 만들어야 할 때
- AI 답변이 장황하고 실무감이 없을 때

### 이 작업지시서로 기대할 수 있는 결과
- 한 줄 요약
- 배경
- 현재 상황
- 핵심 이슈
- 제안 또는 다음 행동

### 언제 쓰는지
- 첫 초안 작성 단계
- 보고용 문서 구조를 처음 잡는 시점

### 바로 복사할 본문
```text
지금 저는 [업무 주제]에 대한 보고서 초안을 정리해야 합니다.
이 문서는 [상사 / 팀원 / 고객 / 이해관계자]가 읽을 예정입니다.
보고 목적은 [현황 공유 / 문제 보고 / 제안 / 실행 계획 정리]입니다.
이 문서를 읽는 사람이 가장 먼저 이해해야 하는 것은 [핵심 이슈 / 제안 / 요청 사항]입니다.

먼저 이 문서에 꼭 들어가야 할 핵심 항목이 있다면 질문해 주세요.
그 다음 아래 형식으로 보고서 초안을 작성해 주세요.

1. 한 줄 요약
2. 배경
3. 현재 상황
4. 핵심 이슈
5. 제안 또는 다음 행동

답변은 실무 문서처럼 단정하고 명확하게 정리해 주세요.
불필요하게 장황하지 않게 쓰되, 실제 공유 가능한 수준으로 내용 밀도를 유지해 주세요.
읽는 사람이 빠르게 판단할 수 있도록 중요한 내용을 앞쪽에 배치해 주세요.
```

### 바꿔야 할 부분
- `[업무 주제]`: 예) 신규 서비스 출시 준비, 콘텐츠 운영 계획
- `[상사 / 팀원 / 고객 / 이해관계자]`: 실제 독자
- `[현황 공유 / 문제 보고 / 제안 / 실행 계획 정리]`: 문서 목적
- `[핵심 이슈 / 제안 / 요청 사항]`: 우선 이해 포인트

### 후속 질문
- 이 문서를 임원 보고용으로 더 짧게 다시 정리해줘.
- 핵심 이슈 3개가 먼저 보이도록 요약형 버전도 추가해줘.

### 수정 요청
- 문장을 더 단정하게 바꾸고 군더더기를 줄여줘.
- 읽는 사람이 바로 의사결정할 수 있게 제안 부분을 더 선명하게 써줘.

### 검수 요청
- 이 보고서에서 빠진 핵심 항목이 있는지 점검해줘.
- 상사가 읽었을 때 바로 이해하기 어려운 부분이 있는지 검수해줘.

### 자주 하는 실수
- 배경 설명이 너무 길어진다
- 핵심 이슈보다 설명이 먼저 나온다
- 독자가 누구인지 정하지 않고 문서를 만든다

### 이 순서에서 쓰면 좋습니다
1. 이 작업지시서로 기본 구조를 만든다
2. 요약본 압축형 작업지시서로 줄인다
3. 최종 검수형 작업지시서로 제출 전 점검한다

### 사용 팁
보고서는 `길게 잘 쓰는 것`보다 `읽는 사람이 빨리 이해하는 것`이 더 중요합니다.  
한 줄 요약과 핵심 이슈가 약하면 본문을 아무리 잘 써도 체감 품질이 떨어집니다.

## 3. 기능 요구사항을 처음 정리하고 싶을 때

### 한 줄 설명
비개발자도 기능 아이디어를 개발자에게 전달 가능한 수준으로 정리하게 돕는 요구사항 정리형 작업지시서입니다.

### 이런 상황에서 특히 잘 맞습니다
- 만들고 싶은 기능은 있는데 설명이 안 잡힐 때
- 기능 정의를 문서로 정리해야 할 때
- MVP 범위와 확장 범위를 분리해야 할 때

### 이 작업지시서로 기대할 수 있는 결과
- 문제 정의
- 사용자 흐름
- 핵심 요소
- MVP 범위
- 확장 가능 요소
- 개발자 전달용 요약

### 언제 쓰는지
- 개발 요청 전 요구사항 정리 단계
- 기획 초안에서 구현 범위를 좁혀야 할 때

### 바로 복사할 본문
```text
지금 저는 [서비스 또는 화면]에 들어갈 [기능]을 정의하고 싶습니다.
이 기능의 목적은 [사용자 문제 해결 / 운영 효율 / 전환율 개선 / 사용성 개선]입니다.
현재 가장 중요하게 보고 싶은 것은 [사용자 흐름 / 핵심 요소 / MVP 범위 / 개발자 전달용 요구사항]입니다.

먼저 이 기능을 정의하기 전에 꼭 확인해야 할 질문이 있다면 먼저 물어봐 주세요.
그 다음 아래 형식으로 기능 정의를 정리해 주세요.

1. 이 기능이 해결하려는 문제
2. 사용자가 이 기능을 쓰는 흐름
3. 꼭 필요한 핵심 요소
4. MVP에서 우선 구현할 범위
5. 추후 확장 가능 요소
6. 개발자에게 전달할 수 있는 요구사항 요약

답변은 비개발자도 이해할 수 있게 설명하되, 개발자가 읽어도 바로 작업을 시작할 수 있을 정도로 구체적으로 써주세요.
애매한 표현보다 실제 화면이나 동작이 떠오르는 설명을 우선해 주세요.
```

### 바꿔야 할 부분
- `[서비스 또는 화면]`: 예) AI시킴 결과 페이지, 결제 페이지
- `[기능]`: 예) 이메일 수집 폼, 결제 버튼, 복사 기능
- `[사용자 문제 해결 / 운영 효율 / 전환율 개선 / 사용성 개선]`: 기능 목적
- `[사용자 흐름 / 핵심 요소 / MVP 범위 / 개발자 전달용 요구사항]`: 우선 포인트

### 후속 질문
- 위 기능 정의를 개발자 전달용 문서 형식으로 다시 정리해줘.
- 사용자 흐름을 화면 단위로 더 세분화해서 보여줘.

### 수정 요청
- 너무 추상적인 표현은 줄이고 실제 화면 요소 기준으로 써줘.
- 기술 설명보다 먼저 사용자 문제와 목적이 더 잘 보이게 다시 정리해줘.

### 검수 요청
- 이 기능 정의에서 빠진 핵심 요소가 있는지 점검해줘.
- 개발자가 읽었을 때 애매하게 느낄 부분이 있는지 검수해줘.

### 자주 하는 실수
- 기능 이름만 적고 목적을 비워둔다
- MVP 범위와 확장 범위를 섞어서 말한다
- 개발자에게 전달할 언어로 정리하지 못한다

### 이 순서에서 쓰면 좋습니다
1. 이 작업지시서로 기능 정의를 만든다
2. 개발자 전달용 작업지시문 생성형으로 바꾼다
3. 구현안이 나온 뒤 개선 요청형이나 검수형으로 이어간다

### 사용 팁
기능 정의는 “멋있어 보이는 설명”보다 “누가 봐도 오해가 적은 설명”이 중요합니다.  
목적과 MVP 범위가 선명하면 이후 개발 흐름이 훨씬 쉬워집니다.

## 4. 너무 일반적인 답변을 더 구체적으로 바꾸고 싶을 때

### 한 줄 설명
방향은 맞지만 뜬구름 잡는 답변을 실제로 써먹을 수 있는 결과로 바꾸는 수정형 작업지시서입니다.

### 이런 상황에서 특히 잘 맞습니다
- AI 답변이 “맞는 말”인데 바로 못 쓰겠을 때
- 예시나 우선순위가 부족할 때
- 내 상황에 연결된 느낌이 약할 때

### 이 작업지시서로 기대할 수 있는 결과
- 추상적인 부분 진단
- 더 구체적인 결과물
- 실행 가능한 문장
- 상황 맞춤형 보완본

### 언제 쓰는지
- 첫 답변 이후 구체화 단계
- 무료 결과보다 더 좋은 결과를 만들고 싶을 때

### 바로 복사할 본문
```text
지금 답변은 방향은 맞지만, 너무 일반적이라서 실제로 바로 쓰기 어렵습니다.
막연한 설명보다, 제 상황에 실제로 적용할 수 있는 수준으로 더 구체화해 주세요.

특히 아래 기준으로 다시 써주세요.
1. 추상적인 표현을 줄일 것
2. 실제 예시를 넣을 것
3. 바로 실행 가능한 문장으로 바꿀 것
4. 필요하면 항목을 더 세분화할 것
5. 제 상황에 맞는 우선순위를 더 분명하게 보여줄 것

가능하면 "설명"보다 "실제로 바로 쓸 수 있는 결과" 중심으로 다시 정리해 주세요.
필요하면 먼저 이 답변에서 가장 약한 3가지를 짚은 뒤 보완본을 작성해 주세요.
```

### 바꿔야 할 부분
- 필요하면 위 작업지시서 아래에 현재 AI 답변을 함께 붙여 넣기
- 상황에 따라 “내 상황”을 한두 줄 추가 설명하기

### 후속 질문
- 위 답변을 내 상황에 맞는 예시 중심으로 한 번 더 바꿔줘.
- 지금 버전에서 실제로 바로 쓸 수 있는 문장만 따로 뽑아줘.

### 수정 요청
- 설명형 문장을 줄이고 실제 표현으로 다시 써줘.
- 너무 넓은 범위의 조언은 빼고 우선순위가 높은 것만 남겨줘.

### 검수 요청
- 여전히 추상적인 부분이 있는지 점검해줘.
- 이 결과를 초보자가 바로 써먹을 수 있는 수준인지 검수해줘.

### 자주 하는 실수
- 현재 AI 답변 원문을 같이 붙이지 않는다
- “구체적으로”만 말하고 어떤 방식으로 구체화할지 안 적는다
- 답변이 약한 이유를 짚지 않고 바로 다시 써달라고만 한다

### 이 순서에서 쓰면 좋습니다
1. 초안 생성형 작업지시서를 먼저 쓴다
2. 이 작업지시서로 구체화한다
3. 마지막에 검수형 작업지시서로 점검한다

### 사용 팁
좋은 수정 요청은 “다시 써줘”보다 “어디가 약한지 먼저 짚고, 그 기준으로 보완해줘”에 가깝습니다.

## 5. AI 작업을 어떤 순서로 시작해야 할지 모르겠을 때

### 한 줄 설명
처음 질문, 후속 질문, 수정 요청, 검수 질문까지 전체 흐름을 한 번에 설계하는 작업설계형 작업지시서입니다.

### 이런 상황에서 특히 잘 맞습니다
- AI를 처음 써보는 사람
- 무엇부터 물어봐야 할지 전혀 감이 안 올 때
- 단발성 질문이 아니라 결과물을 끝까지 완성하고 싶을 때

### 이 작업지시서로 기대할 수 있는 결과
- 첫 질문 설계
- 후속 질문 흐름
- 수정 요청 흐름
- 검수 질문
- 흔히 놓치는 포인트

### 언제 쓰는지
- 작업을 시작하기 전
- 결과물을 끝까지 만들 전체 구조가 필요할 때

### 바로 복사할 본문
```text
지금 저는 [하고 싶은 작업]을 AI로 진행하고 싶습니다.
하지만 무엇부터 어떤 순서로 시켜야 할지 잘 모르겠습니다.

현재 제가 알고 있는 상황은 다음과 같습니다.
- 목적: [무엇을 만들고 싶은지]
- 대상: [누가 보거나 쓰는지]
- 현재 막힌 부분: [어디서 막히는지]
- 원하는 최종 결과: [어떤 상태를 원하는지]

먼저 이 작업을 잘 진행하기 위해 꼭 확인해야 할 질문을 먼저 해주세요.
그 다음 아래 형식으로 전체 작업 흐름을 설계해 주세요.

1. 첫 질문에서 확인해야 할 것
2. 첫 결과를 받은 뒤 이어서 물어볼 후속 질문
3. 결과가 마음에 안 들 때 수정 요청하는 방법
4. 마지막에 품질을 높이기 위한 검수 질문
5. 사용자가 흔히 놓치는 포인트

답변은 처음 해보는 사람도 그대로 따라갈 수 있게 단계별로 설명해 주세요.
가능하면 각 단계마다 바로 복사해서 쓸 문장 예시도 함께 붙여 주세요.
설명만 하지 말고 실제로 바로 붙여 넣을 수 있는 예시 문장을 우선해서 보여주세요.
```

### 바꿔야 할 부분
- `[하고 싶은 작업]`: 예) 블로그 글쓰기, 보고서 작성, 기능 정의
- `[무엇을 만들고 싶은지]`: 실제 목적
- `[누가 보거나 쓰는지]`: 대상
- `[어디서 막히는지]`: 현재 문제
- `[어떤 상태를 원하는지]`: 원하는 결과

### 후속 질문
- 위 흐름을 더 짧게 핵심 단계만 남겨서 다시 정리해줘.
- 각 단계에서 실패하기 쉬운 포인트까지 같이 알려줘.

### 수정 요청
- 설명형 문장을 줄이고 실제 복사해서 쓸 문장 중심으로 다시 정리해줘.
- 단계별 목적이 더 분명하게 보이도록 순서를 다시 다듬어줘.

### 검수 요청
- 이 흐름에서 빠진 핵심 단계가 있는지 점검해줘.
- 초보자가 따라가다가 막힐 만한 구간이 있는지 검수해줘.

### 자주 하는 실수
- 현재 목적과 대상을 안 적는다
- 원하는 최종 결과가 불분명하다
- 한 번의 질문으로 완성하려고 한다

### 이 순서에서 쓰면 좋습니다
1. 이 작업지시서로 전체 흐름을 잡는다
2. 초안 생성형 또는 기능 정의형 작업지시서로 들어간다
3. 수정 요청형과 검수형으로 마무리한다

### 사용 팁
이 작업지시서는 “결과물 하나”보다 “AI를 어떻게 써야 할지의 흐름”을 잡아주는 데 더 큰 가치가 있습니다.  
초보자일수록 이 흐름을 먼저 잡아두면 이후 결과 품질 차이가 크게 납니다.
