# AI시킴 스타터팩 대표 5개 프리미엄 초안 v2-c

## 1. 문서 목적
이 문서는 스타터팩 우선 제작 15개 중 3단계 대표 5개를 `실제 판매 기준`에 맞춰 고도화한 프리미엄 초안입니다.  
1단계, 2단계 프리미엄 초안과 함께 스타터팩 우선 제작 15개를 모두 `실제 돈 받고 팔 수 있는 기준선`으로 올리는 것이 목적입니다.

## 2. 이 문서의 사용 방식
- 이미 초안이나 결과물이 어느 정도 있는 상태에서 가장 큰 힘을 발휘합니다.
- `바로 복사할 본문`으로 먼저 개선 방향을 잡습니다.
- 결과가 조금 나아지면 `후속 질문`으로 더 정교하게 만듭니다.
- 여전히 약하면 `수정 요청`으로 다시 압축합니다.
- 마지막엔 `검수 요청`으로 제출/공유 가능한 수준인지 확인합니다.

## 1. 글 초안을 대상 독자에 맞게 다시 다듬고 싶을 때

### 한 줄 설명
이미 써둔 글 초안을 특정 독자에게 더 잘 맞게 바꾸어, 읽힘과 공감도를 높이는 독자 맞춤형 작업지시서입니다.

### 이런 상황에서 특히 잘 맞습니다
- 글 초안은 있는데 독자와 잘 안 맞는 느낌이 들 때
- 초안이 너무 넓은 사람을 대상으로 쓰인 것 같을 때
- 같은 내용을 더 초보자 친화적 또는 더 전문적으로 바꾸고 싶을 때

### 이 작업지시서로 기대할 수 있는 결과
- 독자와 어긋나는 부분 진단
- 독자 맞춤 수정 방향
- 더 잘 읽히는 최종본
- 공감이 강해진 도입과 흐름

### 언제 쓰는지
- 글 초안이 이미 나온 뒤
- 대상 독자를 더 분명히 맞추고 싶을 때

### 바로 복사할 본문
```text
아래 글 초안은 기본 내용은 갖춰졌지만, 제가 원하는 독자에게는 아직 충분히 맞춰져 있지 않습니다.
이번 글의 핵심 독자는 [대상 독자]입니다.
이 독자는 [현재 상황 / 수준 / 관심사 / 자주 겪는 문제]를 가지고 있습니다.

먼저 이 독자가 이 글을 읽을 때 가장 중요하게 느낄 포인트가 무엇인지 짧게 정리해 주세요.
그 다음 아래 기준으로 글을 다시 다듬어 주세요.

1. 독자가 바로 공감할 표현으로 바꿀 것
2. 너무 일반적인 설명은 줄일 것
3. 독자가 궁금해할 순서대로 흐름을 조정할 것
4. 어려운 표현은 독자 수준에 맞게 조정할 것
5. 이 독자가 실제로 행동하게 만드는 핵심 문장을 더 선명하게 만들 것

답변은 아래 순서로 작성해 주세요.
1. 지금 글에서 독자와 어긋나는 부분
2. 수정 방향 요약
3. 다듬은 최종본

최종본은 실제 게시하거나 공유할 수 있을 정도로 자연스럽고 읽기 쉽게 정리해 주세요.
```

### 바꿔야 할 부분
- `[대상 독자]`: 예) AI 초보자, 팀 리더, 1인 사업자, 기획자
- `[현재 상황 / 수준 / 관심사 / 자주 겪는 문제]`: 독자 특성 설명
- 아래에 실제 글 초안 붙여 넣기

### 후속 질문
- 지금 버전을 유지한 채 더 초보자 친화적인 말투로 다시 바꿔줘.
- 독자 공감이 더 강하게 느껴지도록 도입부만 한 번 더 다듬어줘.

### 수정 요청
- 너무 설명형인 부분은 줄이고, 독자가 바로 이해할 수 있는 표현으로 바꿔줘.
- 읽는 흐름이 끊기는 문단은 다시 연결해서 자연스럽게 정리해줘.

### 검수 요청
- 이 글이 설정한 독자에게 실제로 잘 맞는지 검수해줘.
- 여전히 독자 입장에서 멀게 느껴질 표현이 있다면 짚어줘.

### 자주 하는 실수
- 독자를 너무 넓게 잡는다
- 독자의 현재 수준을 설명하지 않는다
- 글을 “맞게”만 쓰고 “읽히게”는 안 만든다

### 이 순서에서 쓰면 좋습니다
1. 초안 생성형으로 첫 글을 만든다
2. 이 작업지시서로 독자 맞춤화를 한다
3. 마지막에 검수형으로 전달력을 점검한다

### 사용 팁
독자 맞춤 작업은 문장 몇 개 바꾸는 일이 아니라, “이 사람이 어떤 순서로 이해할까”를 다시 설계하는 일에 가깝습니다.

## 2. 제안서를 읽는 사람이 바로 이해하게 고치고 싶을 때

### 한 줄 설명
길고 복잡한 제안서나 기획안을, 읽는 사람이 핵심을 더 빨리 이해하고 판단할 수 있게 다듬는 설득력 강화형 작업지시서입니다.

### 이런 상황에서 특히 잘 맞습니다
- 제안서가 길고 복잡하게 느껴질 때
- 내용은 맞지만 한 번에 핵심이 안 들어올 때
- 읽는 사람이 “그래서 뭘 제안하는지”를 빨리 이해하길 원할 때

### 이 작업지시서로 기대할 수 있는 결과
- 핵심 메시지 선명화
- 구조 개선 포인트
- 이해가 쉬운 최종본
- 의사결정 포인트가 앞쪽에 보이는 문서

### 언제 쓰는지
- 초안이 이미 있고, 제출 전 설득력을 끌어올리고 싶을 때

### 바로 복사할 본문
```text
아래 문서는 [제안서 / 소개서 / 기획안] 초안입니다.
내용 자체는 있지만, 읽는 사람이 핵심을 한 번에 이해하기에는 다소 복잡하거나 흐름이 약합니다.

이 문서를 읽는 사람은 [대표 / 고객 / 의사결정자 / 팀 리더]입니다.
이 사람이 가장 빠르게 이해해야 하는 것은 [핵심 제안 / 기대 효과 / 차별점 / 실행 가능성]입니다.

먼저 이 문서에서 가장 먼저 눈에 들어와야 할 핵심 메시지를 짧게 정리해 주세요.
그 다음 아래 기준으로 문서를 다시 다듬어 주세요.

1. 핵심 메시지가 앞쪽에서 더 잘 보이게 할 것
2. 중복되거나 흐린 표현은 줄일 것
3. 읽는 사람이 빠르게 판단할 수 있게 구조를 정리할 것
4. 장점과 기대 효과가 선명하게 보이게 할 것
5. "그래서 왜 이걸 해야 하는지"가 더 분명하게 보이게 할 것

답변은 아래 순서로 작성해 주세요.
1. 현재 문서의 이해 방해 요소
2. 구조 개선 방향
3. 다듬은 최종본

최종본은 실제로 상대방에게 제출하거나 공유할 수 있는 수준으로 정리해 주세요.
```

### 바꿔야 할 부분
- `[제안서 / 소개서 / 기획안]`: 문서 종류
- `[대표 / 고객 / 의사결정자 / 팀 리더]`: 읽는 사람
- `[핵심 제안 / 기대 효과 / 차별점 / 실행 가능성]`: 우선 포인트
- 아래에 실제 문서 초안 붙여 넣기

### 후속 질문
- 위 최종본을 유지한 채 1페이지 요약본 형태로도 다시 만들어줘.
- 읽는 사람이 가장 먼저 보게 될 도입부만 더 선명하게 다시 써줘.

### 수정 요청
- 문장을 더 단정하고 명확하게 바꿔줘.
- 장점은 유지하되 과장처럼 보이는 표현은 줄여줘.

### 검수 요청
- 이 문서를 처음 읽는 사람이 핵심을 빠르게 이해할 수 있는지 검수해줘.
- 여전히 흐리거나 중복되는 부분이 있다면 표시해줘.

### 자주 하는 실수
- 핵심 제안보다 배경 설명이 먼저 나온다
- 장점은 있는데 판단 포인트가 약하다
- 독자가 누구인지에 따라 구조를 다르게 잡아야 한다는 점을 놓친다

### 이 순서에서 쓰면 좋습니다
1. 제안서 초안을 먼저 만든다
2. 이 작업지시서로 핵심 메시지와 구조를 정리한다
3. 최종 검수형으로 제출 전 점검한다

### 사용 팁
좋은 제안서는 많이 설명하는 문서가 아니라, “읽는 사람이 빨리 이해하고 판단하게 만드는 문서”입니다.

## 3. 이미 나온 코드나 구현안을 개선 요청하고 싶을 때

### 한 줄 설명
이미 나온 코드나 구현안에서 실제로 더 나아질 부분을 짚고, 더 좋은 방향으로 개선 요청하는 구조 개선형 작업지시서입니다.

### 이런 상황에서 특히 잘 맞습니다
- 이미 코드 초안이 나왔는데 더 좋아질 여지가 클 때
- 구현 방향은 맞지만 구조가 아쉽거나 깔끔하지 않을 때
- AI나 개발자에게 “이 부분을 더 낫게 다듬어 달라”고 요청하고 싶을 때

### 이 작업지시서로 기대할 수 있는 결과
- 우선 개선 포인트
- 유지해도 되는 부분
- 구조적 애매함 진단
- 개선된 코드/구현안

### 언제 쓰는지
- 1차 구현 후 개선 라운드
- 코드가 돌아가지만 만족스럽지 않을 때

### 바로 복사할 본문
```text
아래 코드는/구현안은 기본 동작은 되지만, 아직 완성도가 부족합니다.
완전히 새로 만들기보다 현재 구조를 바탕으로 어떤 부분을 개선해야 하는지 먼저 짚어주세요.

이번 개선의 우선순위는 [가독성 / 구조 정리 / 재사용성 / 사용자 흐름 / 성능 / 문구 품질]입니다.

먼저 아래 순서로 점검해 주세요.
1. 지금 상태에서 가장 먼저 개선해야 할 부분
2. 유지해도 되는 부분
3. 구조적으로 애매한 부분
4. 사용자가 느낄 수 있는 문제

그 다음 아래 방식으로 답변해 주세요.
1. 개선 포인트 요약
2. 왜 고쳐야 하는지 설명
3. 더 나은 수정안 또는 개선된 코드/구현안

가능하면 단순 취향 차이보다, 실제로 더 좋아지는 방향 위주로 정리해 주세요.
필요하면 개선 우선순위까지 함께 제안해 주세요.
```

### 바꿔야 할 부분
- `[가독성 / 구조 정리 / 재사용성 / 사용자 흐름 / 성능 / 문구 품질]`: 우선순위 선택
- 아래에 실제 코드나 구현안 붙여 넣기

### 후속 질문
- 지금 개선안에서 가장 효과가 큰 3가지만 우선순위로 다시 정리해줘.
- 코드 수정안 말고, 개발자에게 전달할 개선 요청 문구로도 다시 만들어줘.

### 수정 요청
- 너무 취향적인 지적은 줄이고 실제 영향이 큰 부분만 남겨줘.
- 개선 이유를 더 실무적으로 이해되게 설명해줘.

### 검수 요청
- 이 개선안이 실제로 더 나은 방향인지 검수해줘.
- 빠진 리스크나 놓친 개선 포인트가 있다면 보완해줘.

### 자주 하는 실수
- 코드 원문 없이 요약만 붙여 넣는다
- 무엇을 우선 개선할지 정하지 않는다
- “예쁘게 정리”와 “실제로 좋아짐”을 혼동한다

### 이 순서에서 쓰면 좋습니다
1. 기능 정의형 또는 전달형 작업지시서로 구현을 만든다
2. 이 작업지시서로 개선 포인트를 잡는다
3. 검수형으로 리스크를 마지막 점검한다

### 사용 팁
개선 요청은 “전부 바꿔줘”보다 “뭐부터 고치면 가장 좋아지는지”를 묻는 방식이 훨씬 유용합니다.

## 4. 최종 제출 전 품질 체크를 받고 싶을 때

### 한 줄 설명
거의 완성된 결과물을 제출 직전에 마지막으로 점검해서, 빠진 요소나 어색한 부분을 걸러내는 최종 검수형 작업지시서입니다.

### 이런 상황에서 특히 잘 맞습니다
- 거의 완성된 결과물을 제출/공유하기 직전일 때
- 큰 오류는 없지만 찜찜한 느낌이 들 때
- 스스로는 놓친 부분을 마지막으로 확인하고 싶을 때

### 이 작업지시서로 기대할 수 있는 결과
- 전체 평가 요약
- 꼭 수정해야 할 부분
- 개선하면 더 좋아지는 부분
- 가능하면 반영된 개선본

### 언제 쓰는지
- 제출 직전
- 마지막 품질 점검 단계

### 바로 복사할 본문
```text
아래 결과물은 거의 완성된 상태이며, 최종 제출 전에 마지막 품질 체크를 받고 싶습니다.

이 결과물의 목적은 [보고 / 공유 / 게시 / 제안 / 전달]입니다.
읽는 사람은 [상사 / 고객 / 사용자 / 팀원 / 일반 독자]입니다.

아래 기준으로 최종 검수를 진행해 주세요.
1. 빠진 핵심 요소가 없는지
2. 이해하기 어려운 부분이 없는지
3. 표현이 어색하거나 흐린 부분이 없는지
4. 논리 흐름이 끊기는 부분이 없는지
5. 제출/공유 전에 바로 고치면 좋은 부분이 있는지

답변은 아래 순서로 작성해 주세요.
1. 전체 평가 요약
2. 꼭 수정해야 할 부분
3. 수정하면 더 좋아지는 부분
4. 가능하면 반영한 개선본

검수는 지나치게 칭찬 위주보다, 실제로 더 좋아질 수 있는 부분을 중심으로 해주세요.
필요하면 "지금 제출해도 되는지"에 대한 짧은 판단도 함께 주세요.
```

### 바꿔야 할 부분
- `[보고 / 공유 / 게시 / 제안 / 전달]`: 결과물 목적
- `[상사 / 고객 / 사용자 / 팀원 / 일반 독자]`: 대상 독자
- 아래에 실제 결과물 붙여 넣기

### 후속 질문
- 꼭 수정해야 할 부분만 우선순위 순으로 다시 정리해줘.
- 개선본을 반영한 뒤, 마지막으로 한 번 더 짧게 검수해줘.

### 수정 요청
- 사소한 표현보다 실제 영향이 큰 수정 포인트만 먼저 보여줘.
- 읽는 사람이 오해할 수 있는 부분 중심으로 다시 검수해줘.

### 검수 요청
- 이 결과물이 지금 상태로 제출 가능한 수준인지 최종 판단해줘.
- 아직 부족하다면 가장 아쉬운 3가지를 짚어줘.

### 자주 하는 실수
- 목적과 독자를 안 적는다
- 전체 평가만 받고 실제 수정 포인트를 안 받는다
- 최종 검수를 “칭찬 받기” 용도로 쓴다

### 이 순서에서 쓰면 좋습니다
1. 초안 생성형/고도화형으로 결과를 만든다
2. 이 작업지시서로 최종 점검한다
3. 필요하면 한 번 더 짧은 재검수를 받는다

### 사용 팁
최종 검수는 결과를 새로 만드는 단계가 아니라, “제출해도 되는지”를 판단하는 단계입니다.

## 5. 전체 작업 흐름을 한 번에 설계하고 싶을 때

### 한 줄 설명
첫 질문부터 후속 질문, 수정 요청, 검수 질문까지 하나의 결과를 끝까지 완성하기 위한 전체 작업 흐름 설계형 작업지시서입니다.

### 이런 상황에서 특히 잘 맞습니다
- 단발성 질문이 아니라 결과물을 끝까지 완성하고 싶을 때
- 처음부터 전체 흐름을 설계해서 덜 헤매고 싶을 때
- AI 활용을 더 체계적으로 해보고 싶을 때

### 이 작업지시서로 기대할 수 있는 결과
- 첫 질문
- 후속 질문
- 수정 요청 질문
- 추가 고도화 질문
- 마지막 품질 검수 질문

### 언제 쓰는지
- 작업 시작 전
- “이번에는 처음부터 끝까지 제대로 해보고 싶다”는 시점

### 바로 복사할 본문
```text
지금 저는 [목표 작업]을 AI와 함께 완성하고 싶습니다.
한 번 질문하고 끝내는 것이 아니라, 처음부터 결과물을 더 잘 만들 수 있도록 전체 작업 흐름을 설계해 주세요.

현재 제가 알고 있는 상황은 다음과 같습니다.
- 목적: [무엇을 만들고 싶은지]
- 대상: [누가 보거나 쓰는지]
- 현재 막힌 부분: [어디서 막히는지]
- 원하는 최종 결과: [어떤 상태를 원하는지]

먼저 이 작업을 시작하기 전에 꼭 확인해야 할 질문이 있다면 먼저 제시해 주세요.
그 다음 아래 순서로 전체 흐름을 설계해 주세요.

1. 첫 질문
2. 첫 결과를 받은 뒤 이어갈 후속 질문
3. 결과가 약할 때 수정 요청하는 질문
4. 완성도를 높이기 위한 추가 질문
5. 마지막 품질 검수 질문

각 단계마다 왜 필요한지도 짧게 설명해 주세요.
가능하면 각 단계마다 바로 복사해서 쓸 문장 예시도 함께 붙여 주세요.
설명만 길게 하지 말고, 실제로 그대로 따라할 수 있는 흐름으로 정리해 주세요.
```

### 바꿔야 할 부분
- `[목표 작업]`: 예) 블로그 글 완성, 보고서 작성, 기능 정의, 제안서 고도화
- `[무엇을 만들고 싶은지]`: 실제 목적
- `[누가 보거나 쓰는지]`: 대상
- `[어디서 막히는지]`: 현재 문제
- `[어떤 상태를 원하는지]`: 원하는 완성 결과

### 후속 질문
- 위 흐름을 더 짧은 실전형 버전으로 다시 줄여줘.
- 각 단계에서 실패하기 쉬운 포인트까지 같이 설명해줘.

### 수정 요청
- 설명보다 실제 복사할 문장 예시에 더 집중해서 다시 정리해줘.
- 단계 간 차이가 더 분명하게 보이도록 흐름을 다시 다듬어줘.

### 검수 요청
- 이 흐름만 따라가도 결과물을 끝까지 만들 수 있는지 검수해줘.
- 빠진 단계가 있다면 보완해줘.

### 자주 하는 실수
- 목적은 있는데 대상과 최종 결과가 불분명하다
- 수정 요청 단계를 빼먹는다
- 첫 질문만 정리하고 후속 흐름을 안 만든다

### 이 순서에서 쓰면 좋습니다
1. 이 작업지시서로 전체 흐름을 잡는다
2. 각 단계에 맞는 카테고리 작업지시서로 들어간다
3. 마지막에 검수형으로 마무리한다

### 사용 팁
이 작업지시서는 단일 작업지시서가 아니라 “AI를 쓰는 전체 방식”을 바꾸는 데 더 큰 가치가 있습니다.  
결과물이 중요한 작업일수록, 처음부터 이 흐름을 잡아두는 편이 훨씬 강합니다.
