# AI시킴 스타터팩 나머지 35개 4차 초안 v1

## 1. 문서 목적
이 문서는 스타터팩 나머지 35개 중 4차 우선 제작 항목을 실제 판매 기준에 맞춰 작성한 실물 초안입니다.  
남은 항목들 중에서도 실제 사용 빈도가 높고, 유료팩 체감 가치를 크게 올릴 수 있는 작업지시서를 먼저 확장하는 데 목적이 있습니다.

## 2. 이번 4차 초안에 포함한 항목
1. 완성된 글을 전체 검수하고 수정하고 싶을 때
2. 완성된 보고서나 기획서를 최종 검수하고 싶을 때
3. MVP 범위와 추후 확장 범위를 나누고 싶을 때
4. 코드를 직접 짜기 전 구조 제안을 받고 싶을 때
5. 읽기 쉬운 구조로 다시 나누고 싶을 때
6. AI 답변이 뻔할 때 더 깊은 답을 끌어내고 싶을 때
7. 수정 요청을 어떻게 이어갈지 설계하고 싶을 때

---

## 1. 완성된 글을 전체 검수하고 수정하고 싶을 때

### 한 줄 설명
거의 완성된 블로그 글이나 콘텐츠 초안을 게시 직전에 한 번 더 점검하고, 흐름·표현·전달력을 동시에 다듬는 최종 검수형 작업지시서입니다.

### 이럴 때 가장 먼저 꺼내 쓰세요
- 글은 거의 다 끝났고 게시 직전 `지금 내보내도 되나`를 판단하고 싶을 때
- 누락 점검을 넘어서, 독자 흐름과 전달력까지 마지막으로 다듬고 싶을 때

### 이 항목이 다른 항목과 다른 점
이 항목은 빠진 요소만 찾는 점검형이 아니라, `제목-도입부-본문-마무리` 전체 연결감과 게시 직전 완성도를 함께 보는 최종 검수용입니다.

### 이런 상황에서 특히 잘 맞습니다
- 글은 완성됐지만 뭔가 아쉽다는 느낌이 들 때
- 제목, 도입부, 본문, 마무리가 서로 잘 이어지는지 불안할 때
- 게시 전에 빠진 포인트나 어색한 표현을 마지막으로 잡고 싶을 때

### 이 작업지시서로 기대할 수 있는 결과
- 전체 글의 약한 부분 진단
- 수정 우선순위
- 더 자연스럽고 읽기 쉬운 최종본

### 언제 쓰는지
- 게시 직전
- 초안, 도입부, 제목, 마무리까지 모두 정리된 뒤 최종 점검 단계

### 바로 복사할 본문
```text
아래 글은 거의 완성된 상태이며, 게시 전에 마지막으로 전체 검수와 수정 방향 점검을 받고 싶습니다.

이번 글의 주제는 [주제]이고,
대상 독자는 [대상 독자]입니다.
이 글을 읽고 독자가 얻어가야 하는 핵심은 [핵심 메시지]입니다.

아래 기준으로 전체 글을 검수해 주세요.
1. 제목, 도입부, 본문, 마무리가 자연스럽게 이어지는지
2. 중간에 흐름이 끊기거나 약해지는 구간이 있는지
3. 표현이 어색하거나 너무 흔한 부분이 있는지
4. 독자 입장에서 공감이 약한 부분이 있는지
5. 게시 직전에 꼭 고치면 좋은 부분이 무엇인지

답변은 아래 순서로 주세요.
1. 전체 평가 요약
2. 꼭 수정해야 할 부분 3개
3. 수정 방향
4. 가능하면 반영한 최종본
```

### 바꿔야 할 부분
- `[주제]`
- `[대상 독자]`
- `[핵심 메시지]`
- 아래에 실제 글 초안 붙여 넣기

### 후속 질문
- 위 수정본을 유지한 채 더 짧고 강한 버전으로도 다시 정리해줘.
- 도입부와 마무리만 한 번 더 집중적으로 다듬어줘.

### 수정 요청
- 너무 설명형인 부분은 줄이고 읽는 리듬이 더 살아나게 고쳐줘.
- 흔한 표현은 줄이고 실제 경험이 느껴지는 표현으로 바꿔줘.

### 검수 요청
- 이 글이 지금 상태로 게시해도 되는 수준인지 최종 판단해줘.
- 게시 직전 기준으로 여전히 약한 부분이 있다면 짚어줘.

### 사용 팁
최종 검수는 “좋은 글인지”보다 “지금 내보내도 괜찮은지”를 판단하는 단계로 보는 것이 좋습니다.

## 2. 완성된 보고서나 기획서를 최종 검수하고 싶을 때

### 한 줄 설명
거의 다 쓴 보고서나 기획서를 제출 직전에 검토해, 빠진 논리·약한 표현·이해 방해 요소를 마지막으로 걸러내는 작업지시서입니다.

### 이럴 때 가장 먼저 꺼내 쓰세요
- 상사나 고객에게 보내기 직전, 문서가 실제 의사결정에 충분한지 판단받고 싶을 때
- 목차나 초안 채우기는 끝났고, `제출 가능한 수준`인지 마지막으로 확인하고 싶을 때

### 이 항목이 다른 항목과 다른 점
이 항목은 목차 정리나 기획서 초안 작성과 다르게, `논리 흐름·판단 포인트·제출 직전 리스크`를 걸러내는 제출 직전 검수용입니다.

### 이런 상황에서 특히 잘 맞습니다
- 문서는 다 썼는데 설득력이 충분한지 불안할 때
- 빠진 근거나 흐름상 약한 부분이 없는지 확인하고 싶을 때
- 상사나 고객에게 보내기 전 마지막 점검이 필요할 때

### 이 작업지시서로 기대할 수 있는 결과
- 전체 문서 평가
- 빠진 핵심 요소
- 수정 우선순위
- 더 다듬어진 최종본

### 언제 쓰는지
- 제출 직전
- 내부 공유 직전 마지막 검수 단계

### 바로 복사할 본문
```text
아래 문서는 거의 완성된 상태이며, 제출 전에 마지막으로 검수받고 싶습니다.

이 문서의 목적은 [보고 / 제안 / 공유 / 실행안 정리]입니다.
읽는 사람은 [상사 / 팀 / 고객 / 이해관계자]입니다.
이 사람이 가장 먼저 이해해야 하는 것은 [핵심 이슈 / 제안 / 방향 / 요청 사항]입니다.

아래 기준으로 문서를 검수해 주세요.
1. 논리 흐름이 자연스러운지
2. 빠진 핵심 요소가 있는지
3. 읽는 사람이 헷갈릴 만한 부분이 있는지
4. 표현이 너무 약하거나 모호한 부분이 있는지
5. 제출 전에 가장 먼저 고치면 좋은 부분이 무엇인지

답변은 아래 순서로 주세요.
1. 전체 평가 요약
2. 꼭 수정해야 할 부분
3. 보완 방향
4. 가능하면 반영한 최종본
```

### 바꿔야 할 부분
- `[보고 / 제안 / 공유 / 실행안 정리]`
- `[상사 / 팀 / 고객 / 이해관계자]`
- `[핵심 이슈 / 제안 / 방향 / 요청 사항]`
- 아래에 실제 문서 붙여 넣기

### 후속 질문
- 위 문서를 상사 보고용 기준으로 더 짧고 단정하게 다시 다듬어줘.
- 핵심 요약 5문장 버전도 하나 추가해줘.

### 수정 요청
- 문장을 더 단정하게 바꾸고 군더더기를 줄여줘.
- 의사결정 포인트가 더 앞에서 보이게 다시 정리해줘.

### 검수 요청
- 이 문서가 지금 상태로 제출 가능한지 최종 판단해줘.
- 아직 부족하다면 가장 치명적인 3가지를 짚어줘.

### 사용 팁
최종 검수는 새로운 내용을 추가하는 단계보다, 읽는 사람의 판단을 방해하는 요소를 제거하는 단계입니다.

## 3. MVP 범위와 추후 확장 범위를 나누고 싶을 때

### 한 줄 설명
아이디어나 기능 목록이 너무 넓을 때, 지금 꼭 필요한 범위와 나중에 붙일 범위를 나눠서 더 현실적인 계획으로 정리하는 작업지시서입니다.

### 이런 상황에서 특히 잘 맞습니다
- 만들고 싶은 기능이 많은데 우선순위가 안 잡힐 때
- 개발 범위가 계속 커지는 느낌일 때
- 서비스 초기 버전을 더 작고 선명하게 정리하고 싶을 때

### 이 작업지시서로 기대할 수 있는 결과
- MVP 범위
- 제외하거나 뒤로 미룰 항목
- 확장 후보 목록
- 우선 구현 이유

### 언제 쓰는지
- 기능 정의 후
- 개발 범위 조정 단계

### 바로 복사할 본문
```text
지금 저는 [서비스/기능/프로젝트]의 구현 범위를 정리하고 싶습니다.
아이디어는 많지만, 지금 바로 필요한 MVP 범위와 나중에 붙여도 되는 확장 범위를 나누는 것이 필요합니다.

현재 가장 중요한 목적은 [빠른 검증 / 전환율 확인 / 운영 단순화 / 핵심 가치 검증]입니다.
따라서 아래 기준으로 범위를 나눠 주세요.

1. 지금 꼭 넣어야 하는 MVP 항목
2. 지금은 제외해도 되는 항목
3. 추후 확장 후보
4. 왜 그렇게 나누는지 이유
5. 범위를 더 작게 잡아야 하는 리스크가 있다면 무엇인지

답변은 아래 순서로 주세요.
1. 핵심 가치 기준 요약
2. MVP 포함 항목
3. MVP 제외 항목
4. 추후 확장 항목
5. 최종 추천 범위
```

### 바꿔야 할 부분
- `[서비스/기능/프로젝트]`
- `[빠른 검증 / 전환율 확인 / 운영 단순화 / 핵심 가치 검증]`

### 후속 질문
- 위 범위를 더 작게 줄인 초소형 MVP 버전도 다시 제안해줘.
- 반대로 조금 더 여유 있는 2차 범위도 정리해줘.

### 수정 요청
- 구현 난이도보다 검증 가치가 더 잘 보이게 다시 정리해줘.
- 제외 항목이 왜 제외되는지 더 선명하게 써줘.

### 검수 요청
- 이 범위가 실제로 MVP라고 부를 수 있는 수준인지 검수해줘.
- 너무 욕심낸 부분이 있다면 짚어줘.

### 사용 팁
MVP는 “적게 만드는 것”이 아니라 “핵심 가치를 가장 빨리 검증하는 범위”를 만드는 일입니다.

## 4. 코드를 직접 짜기 전 구조 제안을 받고 싶을 때

### 한 줄 설명
구현 전에 컴포넌트, 파일, 페이지, 데이터 흐름 같은 구조를 먼저 제안받아 시행착오를 줄이는 작업지시서입니다.

### 이럴 때 가장 먼저 꺼내 쓰세요
- 기능 정의는 끝났지만 실제 코드를 어떤 구조로 나눌지 감이 없을 때
- 개발자 전달용 작업 지시문보다 한 단계 앞에서, `설계 뼈대`를 먼저 보고 싶을 때

### 이 항목이 다른 항목과 다른 점
이 항목은 기능 정의나 개발 전달 문서가 아니라, `파일/컴포넌트/상태 구조`를 미리 잡아 시행착오를 줄이는 설계 제안용 작업지시서입니다.

### 이런 상황에서 특히 잘 맞습니다
- 바로 코드를 쓰기보다 구조를 먼저 잡고 싶을 때
- 폴더/컴포넌트 분리가 애매할 때
- 나중에 확장 가능한 설계를 먼저 보고 싶을 때

### 이 작업지시서로 기대할 수 있는 결과
- 구조 제안
- 파일 분리 기준
- 페이지/컴포넌트 역할 정리
- 확장 시 유리한 설계 포인트

### 언제 쓰는지
- 구현 직전
- 구조 설계/리뷰 단계

### 바로 복사할 본문
```text
지금 저는 [서비스/기능/화면]을 구현하려고 하지만, 코드를 바로 짜기 전에 구조를 먼저 정리하고 싶습니다.

가장 중요한 것은 [유지보수성 / 단순한 구조 / 재사용성 / 확장성 / 명확한 역할 분리]입니다.
이번 구현에서 예상되는 요소는 [페이지 / 컴포넌트 / 데이터 / 상태 / 유틸]입니다.

아래 기준으로 구조를 제안해 주세요.
1. 파일/폴더를 어떻게 나누면 좋은지
2. 어떤 컴포넌트가 필요할지
3. 어떤 부분은 분리하고 어떤 부분은 단순하게 유지할지
4. 지금 단계에서 과도한 구조화가 될 위험은 없는지

답변은 아래 순서로 주세요.
1. 전체 구조 제안
2. 파일/폴더 예시
3. 역할 분리 기준
4. 구현 전 주의할 점
```

### 바꿔야 할 부분
- `[서비스/기능/화면]`
- `[유지보수성 / 단순한 구조 / 재사용성 / 확장성 / 명확한 역할 분리]`
- `[페이지 / 컴포넌트 / 데이터 / 상태 / 유틸]`

### 후속 질문
- 위 구조를 MVP 기준으로 더 단순하게 줄여줘.
- 나중에 확장될 수 있는 부분만 따로 표시해줘.

### 수정 요청
- 과한 구조화는 줄이고 현실적인 분리 기준으로 다시 써줘.
- 초보 개발자도 이해하기 쉽게 다시 정리해줘.

### 검수 요청
- 이 구조가 지금 단계에 과한지 적절한지 검수해줘.
- 빠진 핵심 구성 요소가 있다면 짚어줘.

### 사용 팁
구조 제안은 “멋진 아키텍처”보다 “지금 단계에서 덜 꼬이게 만드는 구조”가 더 중요합니다.

## 5. 읽기 쉬운 구조로 다시 나누고 싶을 때

### 한 줄 설명
내용은 괜찮지만 문단과 구조가 답답한 결과물을, 읽는 사람이 더 빠르게 이해할 수 있게 다시 나누는 작업지시서입니다.

### 이런 상황에서 특히 잘 맞습니다
- 정보는 많은데 읽기가 답답할 때
- 문단이 길어서 모바일에서 피로할 때
- 핵심은 있는데 어디서 끊어 읽어야 할지 애매할 때

### 이 작업지시서로 기대할 수 있는 결과
- 더 읽기 쉬운 문단 구조
- 적절한 구분과 위계
- 모바일 기준 가독성 향상

### 언제 쓰는지
- 결과물이 이미 나온 뒤 가독성 보완 단계
- 공유/게시 직전 읽기 흐름 보완 단계

### 바로 복사할 본문
```text
아래 결과물은 내용은 괜찮지만, 읽는 구조가 답답해서 전달력이 떨어집니다.
핵심 내용은 유지하되, 더 읽기 쉽고 이해하기 쉬운 구조로 다시 나눠 주세요.

특히 아래 기준으로 정리해 주세요.
1. 긴 문단은 적절히 나눌 것
2. 같은 성격의 내용은 묶을 것
3. 위계가 보이게 정리할 것
4. 모바일에서도 읽기 쉬운 구조를 고려할 것

답변은 아래 순서로 주세요.
1. 현재 구조의 문제 요약
2. 다시 나눈 구조
3. 읽기 쉽게 정리한 최종본
```

### 바꿔야 할 부분
- 아래에 현재 결과물 원문 붙여 넣기

### 후속 질문
- 위 구조를 더 짧은 문단 중심으로 한 번 더 나눠줘.
- 핵심 메시지가 앞쪽에서 더 잘 보이도록 다시 정리해줘.

### 수정 요청
- 내용은 유지하되 읽기 흐름이 더 살아나게 다듬어줘.
- 문단 간 역할 차이가 더 보이게 바꿔줘.

### 검수 요청
- 이 구조가 실제로 읽기 쉬워졌는지 검수해줘.
- 여전히 답답하게 느껴질 수 있는 부분이 있다면 짚어줘.

### 사용 팁
좋은 문장은 길이가 짧은 문장만 뜻하지 않고, 읽는 사람이 “어디서 끊어 읽으면 되는지”가 보이는 구조를 뜻합니다.

## 6. AI 답변이 뻔할 때 더 깊은 답을 끌어내고 싶을 때

### 한 줄 설명
맞는 말이지만 너무 일반적인 AI 답변에서 벗어나, 더 깊고 더 구체적인 답을 끌어내기 위한 심화형 작업지시서입니다.

### 이런 상황에서 특히 잘 맞습니다
- AI가 늘 비슷한 말만 반복할 때
- 정보는 맞는데 차별성이나 깊이가 부족할 때
- 한 단계 더 생각한 답이 필요할 때

### 이 작업지시서로 기대할 수 있는 결과
- 더 깊은 관점
- 흔한 답변을 넘어선 포인트
- 예시와 맥락이 살아 있는 심화 답변

### 언제 쓰는지
- 첫 답변 이후 심화 단계
- 결과 품질을 한 단계 더 끌어올리고 싶을 때

### 바로 복사할 본문
```text
지금 답변은 방향은 맞지만 너무 일반적이고 뻔합니다.
이번에는 누구나 할 수 있는 말이 아니라, 더 깊이 있고 실제로 도움이 되는 답을 받고 싶습니다.

아래 기준으로 다시 답해 주세요.
1. 흔한 일반론은 줄일 것
2. 실제 맥락과 연결된 설명을 넣을 것
3. 표면적인 조언보다 한 단계 더 들어간 관점을 제시할 것
4. 가능하면 예시나 비교를 붙일 것

답변은 아래 순서로 주세요.
1. 기존 답변이 뻔하게 느껴지는 이유
2. 더 깊게 봐야 할 포인트
3. 심화된 최종 답변
```

### 바꿔야 할 부분
- 필요하면 아래에 기존 답변 원문을 함께 붙여 넣기

### 후속 질문
- 위 답변을 내 상황 기준으로 더 구체적으로 연결해줘.
- 지금 포인트 중 실제 행동으로 옮길 수 있는 것만 다시 정리해줘.

### 수정 요청
- 추상적 통찰보다 실제 적용 가능한 내용에 더 집중해줘.
- 깊이는 유지하되 지나치게 장황하지 않게 줄여줘.

### 검수 요청
- 이 답변이 정말 이전보다 더 깊은지 검수해줘.
- 여전히 일반론처럼 느껴질 수 있는 부분이 있다면 짚어줘.

### 사용 팁
“더 깊게”는 더 어려운 말을 해달라는 뜻이 아니라, 더 실전적인 관점과 더 좋은 판단 기준을 달라는 뜻에 가깝습니다.

## 7. 수정 요청을 어떻게 이어갈지 설계하고 싶을 때

### 한 줄 설명
첫 결과가 나온 뒤 어떤 순서와 기준으로 수정 요청을 이어가야 할지 설계하는 수정 흐름형 작업지시서입니다.

### 단계 태그
`수정`

### 이럴 때 가장 먼저 꺼내 쓰세요
- 첫 결과는 나왔지만 어떻게 고쳐달라고 해야 할지 매번 막연할 때
- 단일 수정 요청이 아니라 `수정의 순서`와 `판단 기준`까지 정리하고 싶을 때

### 이 항목이 다른 항목과 다른 점
이 항목은 후속 질문 흐름처럼 더 묻는 단계가 아니라, `나온 결과를 어떤 순서로 고쳐가야 하는지`를 설계하는 수정 단계 전용 작업지시서입니다.

### 이런 상황에서 특히 잘 맞습니다
- 첫 결과는 나왔는데 어떻게 고쳐달라고 해야 할지 모르겠을 때
- 수정 요청이 늘 막연하거나 반복될 때
- 결과를 끝까지 다듬는 흐름이 필요할 때

### 이 작업지시서로 기대할 수 있는 결과
- 수정 요청 단계 설계
- 어떤 상황에서 어떤 수정 요청을 해야 하는지 기준
- 바로 복사해서 쓸 수정 요청 문장

### 언제 쓰는지
- 첫 답변 이후 보완 단계
- 결과 완성도 끌어올리기 단계

### 바로 복사할 본문
```text
지금 저는 [작업 주제]에 대해 첫 결과를 받은 상태입니다.
문제는 결과가 완벽하지 않은데, 어떤 순서로 수정 요청을 이어가야 할지 모르겠다는 점입니다.

현재 가장 자주 부족한 부분은 [너무 일반적임 / 구조가 약함 / 톤이 안 맞음 / 예시가 부족함 / 전달력이 약함]입니다.

아래 기준으로 수정 요청 흐름을 설계해 주세요.
1. 어떤 부분을 먼저 고쳐야 하는지
2. 어떤 상황에서 어떤 수정 요청 문장을 써야 하는지
3. 수정 요청을 몇 단계로 나누면 좋은지
4. 마지막에는 어떤 기준으로 마무리 검수를 해야 하는지

답변은 아래 순서로 주세요.
1. 수정 요청 4단계 흐름
2. 각 단계의 목적
3. 바로 복사해서 쓸 수정 요청 문장
```

### 바꿔야 할 부분
- `[작업 주제]`
- `[너무 일반적임 / 구조가 약함 / 톤이 안 맞음 / 예시가 부족함 / 전달력이 약함]`

### 후속 질문
- 위 흐름을 더 짧고 실전형으로 다시 줄여줘.
- 초보자 기준으로 더 쉽게 따라갈 수 있게 다시 정리해줘.

### 수정 요청
- 설명형 부분은 줄이고 수정 요청 문장 자체를 더 강화해줘.
- 단계 간 차이가 더 잘 보이게 다시 정리해줘.

### 검수 요청
- 이 흐름만 따라가도 결과를 충분히 다듬을 수 있는지 검수해줘.
- 빠진 핵심 수정 단계가 있다면 보완해줘.

### 사용 팁
수정 요청은 “다시 써줘”보다 “무엇을, 어떤 기준으로, 어떤 순서로 고칠지”가 분명할수록 훨씬 강해집니다.
