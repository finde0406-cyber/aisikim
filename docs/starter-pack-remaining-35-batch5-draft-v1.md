# AI시킴 스타터팩 나머지 35개 5차 초안 v1

## 1. 문서 목적
이 문서는 스타터팩 나머지 35개의 마지막 묶음을 실제 판매 기준에 맞춰 작성한 실물 초안입니다.  
이 문서까지 완성되면, 스타터팩 50개 전체가 최소한 모든 항목에 대해 본문을 갖춘 상태가 됩니다.

## 2. 이번 5차 초안에 포함한 항목
1. API 연동 작업을 설명하고 싶을 때
2. 개발 결과물을 최종 검수하고 싶을 때
3. 추상적인 표현을 실제 예시 중심으로 바꾸고 싶을 때
4. 더 설득력 있게 다시 쓰고 싶을 때
5. 여러 수정 버전 중 더 나은 방향을 판단하고 싶을 때
6. 검수 질문을 어떻게 던질지 정리하고 싶을 때
7. 같은 작업을 다른 AI 도구에 맞게 바꾸고 싶을 때

---

## 1. API 연동 작업을 설명하고 싶을 때

### 한 줄 설명
API 연동이 필요한 기능이나 흐름을 비개발자도 이해할 수 있으면서 개발자 전달용으로도 쓸 수 있게 정리하는 작업지시서입니다.

### 이럴 때 가장 먼저 꺼내 쓰세요
- 기능 요구사항은 정리됐는데 외부 서비스와 연결되는 지점을 설명하기 어려울 때
- 개발자 전달 문서 전에 `왜 이 연동이 필요한지`와 `어디서 호출되는지`를 분명히 하고 싶을 때

### 이 항목이 다른 항목과 다른 점
이 항목은 기능 자체를 정의하는 문서가 아니라, `연동 목적·호출 지점·예외 상황`을 사용자 흐름 기준으로 설명하는 API 맥락 정리용입니다.

### 이런 상황에서 특히 잘 맞습니다
- 어떤 API를 왜 붙이는지 설명이 애매할 때
- 외부 서비스와 내부 기능 연결 흐름을 정리해야 할 때
- 기획자나 운영자가 개발자에게 연동 맥락을 전달해야 할 때

### 이 작업지시서로 기대할 수 있는 결과
- 연동 목적
- 사용자 흐름 안에서 API가 필요한 지점
- 요청/응답 관점의 설명
- 개발자 전달용 정리본

### 언제 쓰는지
- 기능 정의 이후 연동 범위를 설명하는 단계
- 개발자 전달 전 연동 맥락을 정리할 때

### 바로 복사할 본문
```text
지금 저는 [서비스/기능]에 [API 또는 외부 서비스]를 연동하는 작업을 설명하고 싶습니다.
가장 중요한 것은 기술 용어를 늘어놓는 것이 아니라, 왜 이 연동이 필요한지와 어떤 흐름에서 쓰이는지를 분명히 정리하는 것입니다.

현재 목적은 [데이터 조회 / 제출 처리 / 알림 발송 / 외부 결제 연동 / 자동 발송 / 상태 확인]입니다.
사용자 입장에서 가장 중요한 흐름은 [어떤 행동 후 어떤 결과가 보여야 하는지]입니다.

아래 기준으로 연동 설명을 정리해 주세요.
1. 왜 이 API 연동이 필요한지
2. 사용자 흐름 안에서 어디서 호출되는지
3. 어떤 데이터가 오가야 하는지
4. 실패 시 어떤 예외 상황이 있는지
5. 개발자에게 전달 가능한 설명 요약

답변은 아래 순서로 주세요.
1. 연동 목적 요약
2. 사용자 흐름 기준 설명
3. 요청/응답 관점 핵심 포인트
4. 개발자 전달용 요약 문장
```

### 바꿔야 할 부분
- `[서비스/기능]`
- `[API 또는 외부 서비스]`
- `[데이터 조회 / 제출 처리 / 알림 발송 / 외부 결제 연동 / 자동 발송 / 상태 확인]`
- `[어떤 행동 후 어떤 결과가 보여야 하는지]`

### 후속 질문
- 위 내용을 개발 티켓용 문서 형식으로 더 짧게 다시 정리해줘.
- 실패 시 예외 상황과 대응 방향을 더 자세히 보강해줘.

### 수정 요청
- 기술 설명보다 실제 사용자 흐름이 더 먼저 보이게 다시 써줘.
- 개발자가 오해할 수 있는 애매한 표현은 줄여줘.

### 검수 요청
- 이 설명만으로도 개발자가 연동 목적과 흐름을 이해할 수 있는지 검수해줘.
- 빠진 핵심 연동 포인트가 있다면 짚어줘.

### 사용 팁
API 연동 설명은 “어떤 기술을 쓸지”보다 “왜 필요하고, 어디서 쓰이며, 실패하면 어떻게 되는지”가 먼저 보여야 좋습니다.

## 2. 개발 결과물을 최종 검수하고 싶을 때

### 한 줄 설명
이미 구현된 화면이나 기능 결과물을 출시/공유 직전에 점검해서, 사용자 흐름과 완성도 관점의 마지막 리스크를 찾는 작업지시서입니다.

### 이럴 때 가장 먼저 꺼내 쓰세요
- 기능은 다 만들었는데 배포 전 `실제 사용 리스크`를 마지막으로 걸러내고 싶을 때
- 구조 제안이나 기능 정의는 끝났고, 지금은 결과물을 출고 가능한 상태인지 보고 싶을 때

### 이 항목이 다른 항목과 다른 점
이 항목은 구조 제안이나 API 설명이 아니라, `구현이 끝난 결과물`을 사용자 흐름·예외 처리·배포 리스크 관점에서 검수하는 최종 배포 전 점검용입니다.

### 이런 상황에서 특히 잘 맞습니다
- 기능은 구현됐지만 그대로 배포해도 될지 불안할 때
- 사용자 흐름 기준으로 빠진 부분이 없는지 보고 싶을 때
- 겉보기보다 실제 사용 시 문제가 없는지 점검하고 싶을 때

### 이 작업지시서로 기대할 수 있는 결과
- 최종 리스크 요약
- 사용자 관점의 문제 지점
- 고치면 좋은 우선순위
- 배포 전 최종 점검 포인트

### 언제 쓰는지
- 구현 완료 후
- 테스트/배포 직전 검수 단계

### 바로 복사할 본문
```text
현재 [기능/화면/서비스] 구현은 거의 완료되었고, 배포 또는 공유 전에 최종 검수를 받고 싶습니다.

가장 중요한 것은 [사용자 흐름 / 가독성 / CTA / 오류 처리 / 완성도 / MVP 범위 적합성]입니다.
이번 검수는 보기 좋은지보다, 실제 사용자 입장에서 문제 없이 쓰일 수 있는지에 초점을 맞춰주세요.

아래 기준으로 점검해 주세요.
1. 사용자 흐름이 자연스러운지
2. 빠진 핵심 상태나 예외 처리가 있는지
3. 문구나 UI가 오해를 부르는 부분이 있는지
4. MVP 범위를 넘거나 부족한 부분이 있는지
5. 배포 전 가장 먼저 고치면 좋은 부분이 무엇인지

답변은 아래 순서로 주세요.
1. 전체 평가 요약
2. 꼭 수정해야 할 부분
3. 수정하면 더 좋아지는 부분
4. 지금 배포해도 되는지 짧은 판단
```

### 바꿔야 할 부분
- `[기능/화면/서비스]`
- `[사용자 흐름 / 가독성 / CTA / 오류 처리 / 완성도 / MVP 범위 적합성]`

### 후속 질문
- 위 검수 결과 중 가장 치명적인 3가지만 우선순위로 다시 정리해줘.
- 지금 기준으로는 괜찮은 부분도 같이 짚어줘.

### 수정 요청
- 취향 차이보다 실제 사용자 영향이 큰 부분 중심으로 다시 검수해줘.
- 배포 전 체크 항목처럼 더 분명한 문장으로 바꿔줘.

### 검수 요청
- 이 상태가 정말 배포 가능한 수준인지 한 번 더 검수해줘.
- 빠진 예외 처리나 사용자 혼란 요소가 있다면 보완해줘.

### 사용 팁
최종 검수는 “예쁘다”보다 “실제로 쓰다 막히지 않는다”를 확인하는 단계입니다.

## 3. 추상적인 표현을 실제 예시 중심으로 바꾸고 싶을 때

### 한 줄 설명
맞는 말이지만 추상적으로만 들리는 결과를, 실제 상황과 예시 중심으로 바꿔 이해도와 활용도를 높이는 작업지시서입니다.

### 이런 상황에서 특히 잘 맞습니다
- 설명은 맞는데 감이 안 올 때
- 독자가 “예를 들면?”을 떠올릴 때
- AI 답변이 너무 개념적일 때

### 이 작업지시서로 기대할 수 있는 결과
- 실제 예시가 붙은 설명
- 더 이해하기 쉬운 결과
- 추상적 표현이 줄어든 실전형 문장

### 언제 쓰는지
- 첫 답변 이후 구체화 단계
- 초보자 대상 자료 보완 단계

### 바로 복사할 본문
```text
아래 결과는 방향은 맞지만, 표현이 다소 추상적이라서 실제로 바로 이해하거나 적용하기 어렵습니다.
이번에는 개념 설명보다 실제 예시 중심으로 다시 바꿔 주세요.

아래 기준을 반영해 주세요.
1. 추상적인 표현은 줄일 것
2. 실제 상황 예시를 붙일 것
3. 읽는 사람이 "아, 이런 뜻이구나" 하고 바로 이해할 수 있게 할 것
4. 필요하면 잘못된 예시와 좋은 예시를 비교할 것

답변은 아래 순서로 주세요.
1. 추상적으로 느껴지는 부분 요약
2. 예시 중심으로 바꾼 설명
3. 핵심 예시 2~3개
```

### 바꿔야 할 부분
- 아래에 현재 결과 원문 붙여 넣기

### 후속 질문
- 위 설명을 초보자 기준으로 더 쉬운 예시로 다시 바꿔줘.
- 같은 내용을 업무 상황 예시로도 하나 추가해줘.

### 수정 요청
- 설명을 줄이고 예시 비중을 더 높여줘.
- 읽는 사람이 바로 적용할 수 있게 문장형 예시를 보강해줘.

### 검수 요청
- 이 버전이 이전보다 실제로 더 이해하기 쉬운지 검수해줘.
- 여전히 추상적으로 남은 구간이 있다면 짚어줘.

### 사용 팁
추상적인 설명은 맞아도 오래 남지 않습니다. 예시는 이해를 빠르게 만들고, 실제 활용 가능성도 함께 높입니다.

## 4. 더 설득력 있게 다시 쓰고 싶을 때

### 한 줄 설명
핵심 내용은 유지하면서도 상대가 더 납득하고 움직이게 만드는 방향으로 문장을 강화하는 설득력 보강형 작업지시서입니다.

### 이런 상황에서 특히 잘 맞습니다
- 내용은 맞지만 임팩트가 약할 때
- 제안, 소개, 보고 문서가 밋밋하게 느껴질 때
- 읽는 사람이 “그래서 왜 중요한데?”를 느낄 때

### 이 작업지시서로 기대할 수 있는 결과
- 더 선명한 논리
- 장점과 필요성이 잘 보이는 문장
- 더 설득력 있는 최종본

### 언제 쓰는지
- 초안 이후 고도화 단계
- 제안/보고/소개 문구 강화 단계

### 바로 복사할 본문
```text
아래 결과물은 내용은 맞지만, 읽는 사람을 더 설득하는 힘이 부족합니다.
핵심 내용은 유지하되, 왜 이 내용이 중요한지와 어떤 가치가 있는지가 더 선명하게 보이도록 다시 써주세요.

읽는 사람은 [상사 / 고객 / 사용자 / 팀원 / 일반 독자]입니다.
이 사람이 가장 중요하게 느껴야 하는 것은 [필요성 / 가치 / 차별점 / 실행 이유]입니다.

아래 기준으로 다시 작성해 주세요.
1. 논리가 더 선명하게 보일 것
2. 중요한 메시지가 앞에서 더 잘 드러날 것
3. 장점이나 필요성이 더 쉽게 이해될 것
4. 과장된 표현 없이 설득력만 높일 것

답변은 아래 순서로 주세요.
1. 현재 문서가 덜 설득력 있는 이유
2. 설득력을 높이는 방향
3. 다듬은 최종본
```

### 바꿔야 할 부분
- `[상사 / 고객 / 사용자 / 팀원 / 일반 독자]`
- `[필요성 / 가치 / 차별점 / 실행 이유]`

### 후속 질문
- 위 최종본을 더 짧고 강한 버전으로도 다시 써줘.
- 논리는 유지한 채 말투만 더 친절하게 바꿔줘.

### 수정 요청
- 과장된 느낌 없이 더 설득력 있게 바꿔줘.
- 결론이 더 선명하게 보이게 문장 순서를 다듬어줘.

### 검수 요청
- 이 버전이 실제로 이전보다 더 설득력 있는지 검수해줘.
- 지나치게 일반론처럼 남은 부분이 있다면 짚어줘.

### 사용 팁
설득력은 더 세게 말하는 데서 나오기보다, 상대가 “왜 중요한지”를 더 빨리 이해하게 만드는 데서 나옵니다.

## 5. 여러 수정 버전 중 더 나은 방향을 판단하고 싶을 때

### 한 줄 설명
여러 개선안이나 수정 버전이 나왔을 때, 무엇이 더 나은 방향인지 기준을 세워 비교 판단하는 작업지시서입니다.

### 이럴 때 가장 먼저 꺼내 쓰세요
- 이미 2개 이상 수정안이 있는데 취향이 아니라 목적 적합성 기준으로 고르고 싶을 때
- 다시 쓰기보다 `어떤 버전을 살릴지` 먼저 결정해야 할 때

### 이 항목이 다른 항목과 다른 점
이 항목은 설득력 보강처럼 한 버전을 더 좋게 만드는 작업이 아니라, `여러 버전 중 어떤 방향이 목적에 더 맞는지`를 비교 판단하는 선택용 작업지시서입니다.

### 이런 상황에서 특히 잘 맞습니다
- 버전 A, B, C가 있는데 무엇을 선택해야 할지 애매할 때
- 각 버전의 장단점을 객관적으로 보고 싶을 때
- 감으로 고르지 않고 기준에 따라 결정하고 싶을 때

### 이 작업지시서로 기대할 수 있는 결과
- 버전별 장단점 비교
- 선택 기준 정리
- 가장 추천하는 방향

### 언제 쓰는지
- 수정안이 2개 이상 나왔을 때
- 최종 선택 직전

### 바로 복사할 본문
```text
아래에는 같은 목적을 가진 결과물의 여러 수정 버전이 있습니다.
각 버전 중 무엇이 더 나은 방향인지 판단하고 싶습니다.

이번 결과물의 목적은 [보고 / 게시 / 제안 / 소개 / 전달]입니다.
읽는 사람은 [상사 / 고객 / 사용자 / 팀원 / 일반 독자]입니다.
가장 중요한 판단 기준은 [명확성 / 설득력 / 가독성 / 신뢰감 / 행동 유도]입니다.

아래 기준으로 비교해 주세요.
1. 각 버전의 장점
2. 각 버전의 약점
3. 목적과 독자에 더 잘 맞는 버전
4. 두 버전을 섞으면 더 좋아질 포인트가 있는지

답변은 아래 순서로 주세요.
1. 버전별 비교 요약
2. 가장 추천하는 버전과 이유
3. 필요하면 최적화한 최종 통합본
```

### 바꿔야 할 부분
- `[보고 / 게시 / 제안 / 소개 / 전달]`
- `[상사 / 고객 / 사용자 / 팀원 / 일반 독자]`
- `[명확성 / 설득력 / 가독성 / 신뢰감 / 행동 유도]`
- 아래에 버전 A/B/C 붙여 넣기

### 후속 질문
- 추천 버전을 기준으로 더 다듬은 최종본을 만들어줘.
- A의 장점과 B의 장점을 섞은 통합 버전도 만들어줘.

### 수정 요청
- 취향성 판단보다 목적 적합성 기준으로 다시 비교해줘.
- 장단점이 더 명확히 드러나게 다시 정리해줘.

### 검수 요청
- 이 비교 기준이 충분히 타당한지 검수해줘.
- 놓친 판단 포인트가 있다면 추가해줘.

### 사용 팁
여러 버전 중 고를 때는 “내가 더 좋아 보이는 것”보다 “목적과 독자에 더 맞는 것”을 기준으로 보는 편이 좋습니다.

## 6. 검수 질문을 어떻게 던질지 정리하고 싶을 때

### 한 줄 설명
결과물을 마지막으로 점검할 때 어떤 질문을 던져야 품질이 좋아지는지, 검수 질문 자체를 설계하는 작업지시서입니다.

### 단계 태그
`검수`

### 이럴 때 가장 먼저 꺼내 쓰세요
- 결과물은 거의 끝났지만 어떤 질문으로 마지막 점검을 해야 할지 막막할 때
- “한 번 더 봐줘”가 아니라 실제 판단 가능한 검수 질문 세트를 만들고 싶을 때

### 이 항목이 다른 항목과 다른 점
이 항목은 결과물을 직접 고치는 수정 단계가 아니라, `무엇을 질문해야 품질 문제가 드러나는지`를 설계하는 검수 단계 전용 작업지시서입니다.

### 이런 상황에서 특히 잘 맞습니다
- 마지막 검수를 매번 막연하게 하게 될 때
- “한 번 더 봐줘”보다 더 좋은 질문이 필요할 때
- 결과물 종류에 맞게 검수 질문을 잘 바꾸고 싶을 때

### 이 작업지시서로 기대할 수 있는 결과
- 검수 질문 구조
- 목적별 검수 질문
- 바로 복사해서 쓸 최종 검수 질문 문장

### 언제 쓰는지
- 결과물 마무리 전
- 최종 점검 루틴 만들기 단계

### 바로 복사할 본문
```text
지금 저는 [결과물 종류]를 거의 마무리한 상태이며, 마지막 검수 질문을 더 잘 던지고 싶습니다.

검수의 목적은 [빠진 요소 확인 / 읽기 쉬움 확인 / 설득력 확인 / 제출 가능 여부 판단 / 오류 점검]입니다.
읽는 사람은 [상사 / 고객 / 사용자 / 팀원 / 일반 독자]입니다.

아래 기준으로 검수 질문을 설계해 주세요.
1. 꼭 확인해야 할 핵심 질문
2. 결과물 종류에 맞는 검수 질문
3. 너무 막연하지 않고 실제로 도움이 되는 질문
4. 최종 제출 여부를 판단하는 질문

답변은 아래 순서로 주세요.
1. 검수 질문 5개
2. 그중 가장 중요한 핵심 질문 1개
3. 바로 복사해서 쓸 최종 검수 질문 문장
```

### 바꿔야 할 부분
- `[결과물 종류]`
- `[빠진 요소 확인 / 읽기 쉬움 확인 / 설득력 확인 / 제출 가능 여부 판단 / 오류 점검]`
- `[상사 / 고객 / 사용자 / 팀원 / 일반 독자]`

### 후속 질문
- 위 검수 질문을 더 짧고 실전형으로 다시 줄여줘.
- 초보자도 바로 쓸 수 있게 설명을 더 쉽게 붙여줘.

### 수정 요청
- 막연한 질문은 줄이고 실제로 판단 가능한 질문 중심으로 바꿔줘.
- 결과물 종류에 더 맞는 질문으로 다시 다듬어줘.

### 검수 요청
- 이 검수 질문 세트가 실제 품질 점검에 도움이 되는지 검수해줘.
- 빠진 핵심 검수 관점이 있다면 보완해줘.

### 사용 팁
좋은 검수 질문은 “어때?”가 아니라 “무엇이 빠졌는지, 무엇이 약한지, 지금 내보내도 되는지”를 분명히 묻는 질문입니다.

## 7. 같은 작업을 다른 AI 도구에 맞게 바꾸고 싶을 때

### 한 줄 설명
같은 목적의 작업지시서를 ChatGPT, Claude, Gemini, Codex 등 다른 도구에 넣어도 잘 맞게 조정하는 작업지시서입니다.

### 단계 태그
`변형`

### 이럴 때 가장 먼저 꺼내 쓰세요
- 이미 잘 쓰고 있는 작업지시서가 있는데 다른 AI에도 맞게 옮겨 쓰고 싶을 때
- 결과 비교 실험을 하거나, 특정 도구에서 더 나은 반응을 끌어내고 싶을 때

### 이 항목이 다른 항목과 다른 점
이 항목은 첫 질문을 만드는 단계가 아니라, `이미 있는 작업지시서`를 다른 AI의 응답 성향에 맞춰 재배치하는 변형용 작업지시서입니다.

### 이런 상황에서 특히 잘 맞습니다
- 같은 작업을 여러 AI에서 시험해보고 싶을 때
- 도구마다 결과 톤이나 응답 방식이 달라서 보정이 필요할 때
- 한 작업지시서를 여러 도구에 맞게 재활용하고 싶을 때

### 이 작업지시서로 기대할 수 있는 결과
- 도구별 문장 조정 포인트
- 같은 목적을 유지한 변형 버전
- 여러 AI에서 재활용 가능한 입력문

### 언제 쓰는지
- 기존 작업지시서를 다른 AI에도 써보고 싶을 때
- 결과 비교 실험 단계

### 바로 복사할 본문
```text
지금 저는 아래 작업지시서를 [현재 AI 도구] 기준으로 쓰고 있습니다.
이제 같은 목적을 유지한 채 [다른 AI 도구]에도 더 잘 맞게 바꾸고 싶습니다.

가장 중요한 것은 목적은 유지하되, 도구 특성에 따라 문장 구조와 요청 방식을 조금 더 맞추는 것입니다.

아래 기준으로 작업지시서를 다시 정리해 주세요.
1. 현재 문장에서 그대로 유지해도 되는 부분
2. 다른 AI 도구에 맞게 바꾸면 좋은 부분
3. 더 잘 작동할 가능성이 높은 문장 구조
4. 최종 변형본

답변은 아래 순서로 주세요.
1. 현재 버전과 다른 도구의 차이를 고려한 조정 포인트
2. 수정 방향
3. 최종 변형 작업지시서
```

### 바꿔야 할 부분
- `[현재 AI 도구]`
- `[다른 AI 도구]`
- 아래에 현재 작업지시서 원문 붙여 넣기

### 후속 질문
- 위 변형본을 더 짧은 버전으로도 다시 만들어줘.
- 각 도구별로 조금씩 다르게 조정한 버전 2개를 추가해줘.

### 수정 요청
- 도구 차이는 반영하되 목적이 흔들리지 않게 다시 다듬어줘.
- 표현 차이보다 실제 결과 품질 차이가 날 만한 부분을 더 강조해줘.

### 검수 요청
- 이 변형본이 다른 AI 도구에서도 잘 작동할 가능성이 높은지 검수해줘.
- 여전히 원래 도구에만 최적화된 표현이 남아 있다면 짚어줘.

### 사용 팁
같은 작업이라도 AI마다 결과를 받는 방식이 조금 다를 수 있습니다.  
완전히 새로 쓰기보다, 목적은 유지한 채 문장 구조와 요청 밀도만 조정하는 쪽이 더 효율적입니다.
